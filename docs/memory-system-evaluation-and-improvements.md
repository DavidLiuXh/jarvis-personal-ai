# Jarvis 记忆系统评价与改进建议

这份文档整理了对当前 Jarvis 记忆系统的整体评价、优势、风险点，以及更适合产品化落地的改进建议。

## 1. 总体评价

我的判断是：**这套机制在“个人长期助手”场景里是合理的，成功概率比单纯向量库高不少。**

它不是单一检索技巧，而是把这些能力组合成了一个比较完整的闭环：

- 结构化事实
- 语义检索
- 关键词检索
- 图谱关联
- 人工可纠错
- 高层反思

所以它最大的优点不是某一个算法特别新，而是整个系统很像“真正有机会在产品里跑出效果”的设计。

### 为什么我认为它有机会在应用中获得好结果

1. 它解决了纯向量检索的几个老问题

- 专有名词召回不稳
- 重要但不相似的事实容易被埋掉
- 历史脏数据越积越多
- 用户无法纠错

这套设计通过 `BM25 + embedding + importance + recency + L1 Markdown 可修正`，基本都对着这些问题下手了。

2. 它非常适合“长期个人记忆”场景

如果服务对象是同一个用户，长期对话，主题相对稳定，那么很多事实会反复出现：

- 身份
- 偏好
- 项目约束
- 习惯
- 常见任务

这种场景下，`facts + prewarm + reflect` 往往会比单纯聊天历史回放更好，因为它把“稳定认知”和“近期语境”拆开处理了。

3. 图谱扩展是加分项

`entity_links` 的一跳扩展，在工程上是值得的。它能把“相关但没直接命中的事实”拉回来，在项目型、多主题但围绕同一实体的对话里尤其有价值。

4. `reflect` 有潜力，但需要克制

反思层可以形成高阶 insight，这对长期助手特别有价值。当前实现把 `reflect` 的结果限制在 `insight` 类别，没有直接重写核心 identity/specification，这个边界设计是对的。

## 2. 最强的 3 点

### 2.1 `facts + prewarm` 的双层设计很强

很多系统要么只靠聊天历史，要么只靠结构化记忆。Jarvis 同时保留了两者：

- `facts` 负责稳定、可控、可纠正的长期知识
- `prewarm` 负责召回过去相似场景的原始语境

这会让回答既“记得长期事实”，又“不至于太像数据库查询结果”，很适合个人助手。

### 2.2 混合检索比纯向量方案更稳

`vec_facts + facts_fts + importance + recency` 这套组合很实用。

它能同时覆盖：

- 语义相似
- 专有名词精确命中
- 长期重要事实
- 最近活跃记忆

这比只看 embedding 距离更接近真实产品需求。

### 2.3 `MEMORIES.md` 作为可人工纠错的真相层，非常有产品价值

很多记忆系统最大的问题不是“记不住”，而是“记错了改不了”。这里把 L1 做成可读可改的 Markdown，很关键：

- 用户能看见系统记住了什么
- 用户能手工修正幻觉
- L2/L3 还能从 L1 自愈重建

这会显著提升长期可维护性和用户信任。

## 3. 最可能翻车的 5 点

### 3.1 `importance` 评分如果不稳，会直接把排序带偏

这套机制很依赖 `importance`，但 importance 本质上还是模型或规则打出来的。

一旦出现：

- 不重要的事实被打高分
- 关键事实被打低分

后面的检索融合再漂亮，也是在错的地基上排序。

### 3.2 `accessWeight` 过强时，会把“最近用过”误当成“真正相关”

最近访问过的 fact 会持续升温，这在产品里很常见，但也容易形成记忆偏置：

- 最近常聊的话题越来越容易被召回
- 老但关键的事实被压下去

如果参数不稳，系统会越来越“近视”。

### 3.3 `reflect` 容易生成看起来高级、其实不可靠的 insight

反思层很有吸引力，但也是最容易漂的一层。

风险是：

- 把局部现象总结成长期规律
- 把推测写成事实
- 生成听起来合理但不可验证的抽象洞察

虽然当前实现只覆盖 `insight`，不直接污染核心 facts，这已经是很好的保护，但 insight 本身仍可能误导后续回答。

### 3.4 `entity extraction` 一旦抽错，会把噪声扩散到检索阶段

图谱扩展的收益建立在抽取得准的前提上。

如果错误地把：

- 人和项目连错
- 技术和概念混淆
- 关系类型误判

那么 `expandViaEntityLinks()` 就会把不相关 facts 带进 prompt。图谱机制最大的风险不是“没抽到”，而是“抽错后还参与扩展”。

### 3.5 长期运行后，事实层可能出现“语义重复但粒度不一致”的污染

即使有去重，也很难完全避免这类情况：

- 一条事实很抽象
- 一条事实很具体
- 两条事实不完全重复，但表达的是同一长期结论

这类数据会逐渐积累，导致：

- consolidation 压力变大
- reflect 输入变脏
- prompt 里出现轻微重复或冲突

## 4. 适用与不适用场景

### 更可能成功的场景

- 个人 AI 助手
- 长期项目 copilot
- 投资/研究型助理
- 多渠道统一记忆助手

### 不一定占优的场景

- 一次性短对话
- 高频事实变化、要求强实时性的场景
- 完全开放域知识问答
- 对错误记忆极其敏感、且无人校正的场景

## 5. 如果要做成更稳的产品，最该先改的 5 个点

### 5.1 给 `facts` 增加“证据链”和来源类型

现在的 fact 主要是：

- `category`
- `content`
- `importance`

这还不够产品级稳健。建议至少增加：

- `source_type`
  - `conversation`
  - `session_event`
  - `manual_edit`
  - `reflection`
- `source_ref`
  - 来自哪次 session / 哪个文件 / 哪轮对话
- `confidence`
- `derived_from_fact_ids` 或 `derived_from_session`

这样做的好处：

- 错误记忆可以追溯来源
- `reflect` 生成的 insight 可以和原始事实区分开
- 手工编辑内容可以被优先信任
- 排序时可以提升人工修正事实的稳定性

### 5.2 把 `importance` 从单值改成多因子评分

现在最大的风险之一是 `importance` 太像黑盒总分。

更稳的做法是拆成几个维度，例如：

- `user_identity_weight`
- `project_constraint_weight`
- `recurrence_weight`
- `explicitness_weight`
- `manual_override_weight`

最后再合成总分。

这样做的好处：

- 更容易解释为什么某条 fact 排名高
- 调参更稳，不需要一改全盘漂
- 能让 identity / hard constraint 这类事实长期稳定

一句话说，就是把“重要性”从拍脑袋分值，变成可解释的评分结构。

### 5.3 给 `reflect` 加“保守模式”

这是最建议优先上的保护。

建议包括：

- insight 不直接进入 always inject
- 先给 `insight` 一个较低默认权重
- 要求每条 insight 至少引用 2-3 条底层 facts
- 反思输出里保存 supporting fact ids
- 对“人格判断、长期偏好判断”设置更高门槛

最理想的状态是：

- insight 可以存在
- 但默认只作为辅助认知
- 不要过早变成强行为约束

否则系统很容易出现“说得很像懂你，其实只是过拟合近期样本”。

### 5.4 把图谱扩展做成“可控开关 + 更严格的准入条件”

`entity_links` 有价值，但最容易 silently 变脏。

建议优先做：

- 只允许从高置信度 fact 扩展
- 只允许部分 relation 参与扩展
  - 比如 `works_on`、`uses`、`part_of`
  - 暂时弱化 `interested_in`、`has_habit`
- 对扩展出的 fact 设单独上限
- 在 prompt 中把 graph-expanded facts 单独标记

建议先把图谱当“辅助召回器”，不要太早把它当成“推理核心”。

### 5.5 给检索结果做在线评估和反馈回路

现在最大的产品问题不是“没有好算法”，而是你很难知道：

- 哪些 facts 真正帮到了回答
- 哪些 facts 经常被召回但没价值
- 哪些 insight 在误导模型
- 哪些扩展 facts 是纯噪声

建议至少记录：

- 每轮注入了哪些 facts
- 最终回答用了哪些 facts 的痕迹
- 用户有没有继续追问纠正
- 被注入但长期无效的 facts 是哪些

然后形成简单反馈：

- 经常召回但无贡献的 fact 降权
- 被用户纠正过的 fact 标记风险
- 某些 insight 若连续引发偏题，自动降权或停用

这样系统才能从“静态设计”变成“可进化产品”。

## 6. 如果只能先做 2 件事

如果资源有限，最优先建议：

1. `fact` 增加 `source / confidence / evidence`
2. `reflect` 进入保守模式

因为这两项最直接影响“记忆可信度”。

## 7. 按产品收益排序的改进优先级

建议顺序：

1. `facts` 增加来源、置信度、证据链
2. `reflect` 保守化
3. `importance` 拆成多因子评分
4. `entity_links` 扩展收紧
5. 检索效果埋点与反馈闭环

## 8. 总结

当前这套记忆系统已经具备“能工作”的完整框架。下一步最该做的不是继续堆更复杂的算法，而是系统性提升：

- 可解释性
- 可控性
- 可追溯性
- 可纠偏性

一句话总结：

**当前 Jarvis 记忆系统的方向是对的，真正决定产品上限的，不是检索公式本身，而是 fact 质量、importance 稳定性、reflect 保守性，以及图谱扩展的准确率。**
